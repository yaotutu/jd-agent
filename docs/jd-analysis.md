## 二、核心发现：岗位体系的 5 类结构性问题

### 问题 1：同岗名，跨部门，职责实际不同 ——「同名异义」

最典型的 **"工艺工程师"** 出现在 **3 个部门**，职责完全不同：

| 部门 | 实际岗位名 | 干什么 |
|---|---|---|
| 电池研发中心 | 电池工艺工程师 | 电池制造工艺（材料/涂布/辊压/注液）的研发 |
| 质量管理中心 | 制造工艺工程师 | 生产过程的工艺流程策划、SOP、PFMEA、工装设计 |
| （文件标题写"制造工艺工程师"，但归属质量） | | |

→ **领导招聘时，一句"招个工艺工程师"，三个部门招的是三种人**。这是 P1 的铁证。

类似还有：
- **电子工程师 / 嵌入式硬件工程师 / 嵌入式软件工程师 / 嵌入式软件开发工程师** —— AI 3D 中心里 4 个高度重叠的岗位名，边界不清。
- **电气工程师**（装备研发中心）与 **初级电气工程师/电气总工程师/电气装配工程师**（生产交付）—— "电气"散落在至少 3 个部门。

### 问题 2：「文件夹归属」与「JD 内部写的所属部门」严重不一致 ——「归属错位」

这是最普遍、也最致命的问题。文件夹名 ≠ JD 内部"所属部门"字段：

| 文件夹 | JD 内部"所属部门" | 说明 |
|---|---|---|
| 行政运营中心 | 行政运营中心 | ✅ 一致 |
| 行政运营中心 | PMOC | 项目管理岗挂在行政下 |
| **质量管理中心** | **行政运营中心** | 质量的多个 JD 内部却写"所属部门=行政运营中心"，且上级写"质量管理总监" |
| **质量管理中心** | **设备生产交付中心** | 质量检验工程师内部写属于生产交付 |
| **质量管理中心** | **质量管理中心** | 质量管理经理写对了一半 |
| 财务管理中心 | 计划财务中心 | 文件夹叫"财务"，内部叫"计划财务中心" |
| 全球业务中心 | 国际业务中心 | 文件夹叫"全球"，内部叫"国际" |
| 采购中心 | 采购职能团队 | 又一个叫法 |
| 装备技术研究中心 | 装备研发中心 / 装备研发部门 | 文件夹叫"装备技术研究"，内部叫"装备研发"，且"中心/部门"混用 |
| AI 3D事业中心 | AI3D研发部 / AI 3D事业中心 | 部门混称 |

→ **组织架构本身没有统一命名**。同一个"质量管理"体系，有的叫"质量管理中心"、有的叫"行政运营中心-质量"、有的归"设备生产交付中心"。部门领导自己都搞不清岗位挂在哪，更别说招人。

### 问题 3：直接上级字段混乱/缺失 ——「汇报关系断裂」

- 大量 JD 的"直接上级职位"为空（约 15+ 份完全空缺）。
- 上级称谓不统一：`质量管理总监` / `行政运营中心负责人` / `CEO` / `PMOC主任` / `CPO` / `供应链管理经理` 等多种层级。
- 同一中心内部，有人汇报到"中心负责人"，有人直接汇报到 CEO。

→ **汇报线没有拉齐**，无法判断一个岗位在组织里的层级，招聘时定不了职级。

### 问题 4：岗位名"内外不一致" + "标称 vs 实际"错位

- 文件标题岗位名 ≠ 表内"岗位名称"：
  - 质量管理经理 → 内部岗位名"质量管理专家"
  - 产线策划总工程师 → 内部岗位名"产线策划专家"
  - 人力资源经理 → 内部岗位名"人力资源总监"
  - 采购中心那份（无括号）→ 标题"仓储及物料管理专家"，岗位名"仓库管理员"
  - 项目管理经理 → 内部岗位名"PM项目管理"
- 大量"专家"称谓：产线策划专家、质量管理专家、仓储及物料管理专家…… 高阶岗位用"专家"还是"经理"还是"总工程师"没有规则。

### 问题 5：编制/审核/批准流程未走完（JD 仍是草稿状态）

- 多数 JD 的"编制人/审核人"为空。
- 几乎所有 JD 的"批准人"都是 `[填写批准人姓名]`、生效日期 `[填写生效日期]`。
- 编制日期跨度从 2025.3 到 2026.1，且越新的（如质量线 2025.7）内部归属反而更乱，说明**体系在演进中没收敛**。

## 三、结论：P1/P2 主次判断

回到 `problem-definition.md` 里提出的两个子问题：

- **P1（岗位体系本身缺失/不清）**
- **P2（领导不会用现有 JD 做判断）**

**数据结论：当前主要矛盾是 P1，不是 P2。**

理由：
1. JD 并非"缺失"，75 份覆盖全公司，**数量是够的**。
2. 但岗位体系**结构性混乱**（同名异义、归属错位、汇报断裂、命名不一、流程未走完）。
3. 在这种状态下，**即便给领导一个再好的"匹配工具"也无济于事**——因为工具要匹配的"岗位"本身就是模糊的。
4. 所以领导的"不知道招什么人"，根因是**没有一张可信的岗位地图**，而不是"不会用地图"。

**对后续 skill 设计的含义（重要）：**

skill 不能假设"岗位体系是清晰的"然后去做匹配。它必须先把岗位体系**结构化、去歧义、建立可检索的岗位知识库**，然后才能谈"帮领导找岗位"。

## 四、数据质量问题（影响后续处理）

- 约 6 份 JD 是空壳（`AI 3D电商专员`、`嵌入式硬件工程师`、`高级结构工程师`、生产交付 4 份全部为空壳）—— 文件名有岗位但表内字段全空，需确认是否有内容版。
- HTML 表格格式不统一：有的 `<table>` 嵌在 `<synced-source>` 标签里（采购中心那份），解析时要注意。

## 五、建议的下一步（待用户确认，不擅自执行）

1. **澄清组织架构真相**：14 个文件夹 vs JD 内部部门名，到底哪个是当前生效的组织架构？
   （这一步必须人确认，AI 无法替你判断公司真实架构。）
2. **建立岗位主数据模型**：每个岗位一条标准记录，含「标准岗位名 / 归属部门（唯一）/ 直接上级 / 职级 / 核心职责」，把同名异义和归属错位收敛掉。
3. 在主数据基础上，再设计 skill 帮领导找岗位。
