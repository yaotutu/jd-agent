# 问题定义

> 当前生效定义见下文「核心定义」。P1/P2 的早期辨析已收敛为文末一句话背景，不再展开。

## 核心定义

**我们要解决的问题（一句话）：**

部门领导在招聘时，**不会把"我的业务需求/场景"拆解成"我该招什么岗位、什么级别、什么能力的人"**。

**典型场景（用户原话，重要锚点）：**

> "我要招一个采购，但有淘宝采购、京东采购、定制件采购、标准件采购，
>  我到底要哪种采购？我的采购人员需要具备哪种技能、哪些经验？我不清楚。"

这说明 agent 要解决的不是"给一个岗位名"，而是 **「岗位内部维度的细分拆解」**：

- 一个**岗位大类**（如"采购"）在真实业务里会**细分**成多个方向
  （标准件采购 / 定制件采购 / 电商采购 / 技术采购…）。
- 每个细分方向需要的**技能、经验、归属中心、级别**都不同。
- 部门领导恰恰卡在"我知道要招采购，但不知道是哪一种、要什么能力"。

## 两层拆解模型

| 拆解层 | 说明 | 输入→输出举例 |
|---|---|---|
| **L1 场景→岗位大类** | 业务场景属于哪条价值链、哪个环节 → 该招什么岗位大类 | "要上第一条产线" → 产线策划 / 装备研发 |
| **L2 大类→细分+画像** | 这个岗位大类在公司实际分哪些细分方向，各自要什么技能/经验/级别 | "采购" → 标准件(供应链知识) / 定制件(懂机加工、能看图) / 技术采购 / 电商采购… |

## agent 的核心能力

输入：一个业务场景描述（自然语言，例如"我要给客户上第一条产线""我们要把电池能量密度提上去""产线装配总是出问题"）。

处理：
1. 读懂业务场景属于公司哪条价值链、哪个环节（见 `business-context.md`）。
2. 在现有 75 份 JD（作"能力画像知识库"，**参考性、不作强依据**）中定位相关岗位。
3. 结合业务事实反推：这个场景缺哪些能力？需要什么级别（入门/执行层/中阶/高阶/负责人）？
4. 输出：建议招的岗位（含归属中心）、级别、关键能力要求（每条挂业务依据）、为什么。
5. 收口后可选：调用 jd-generator 产出标准 JD 到 `output/`。

## 关键约束（来自用户）

- **不要去治理岗位体系混乱**——那是百人初创的正常态，不在范围内。
- **JD 作"知识源"用，不作"标准答案"**——JD 由员工自行编写、可能不准；
  能力要求以**业务事实**为主据，JD 仅作印证。详见 `capabilities/reasoning-rules.md` 铁律二。
- **不懂就问，不要猜**；每个结论都要挂业务依据。详见 `reasoning-rules.md` 两条铁律。
- 最终产出形态：一个 agent（开发期，反复测试）；后期 jd-generator 模块可独立成 skill。

## 背景（早期辨析，已收敛，仅作存档）

最初曾把问题拆成 P1（岗位体系本身缺失/混乱，需治理）和 P2（领导不会用 JD 拆解招聘需求），
并据 75 份 JD 分析判断"主问题是 P1、需先治理"。

**用户否决**：公司刚突破百人，职位混乱是正常的，**不治理**；直接做 P2——
"在混乱的真实 JD 之上工作，把多份模糊 JD 当知识源，结合业务场景反推用人"。
完整的 JD 结构性问题分析（同名异义/归属错位等 5 类）见 `jd-analysis.md`，作开发期存档。
