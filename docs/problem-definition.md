## 一、问题陈述

**表层问题：**
公司有几个部门，部门领导在招聘时，**不知道自己需要什么样的人才，或者不知道要用什么样的岗位**。

## 二、问题拆解（核心）

"不知道该招什么人"这句话里藏着**两个本质不同的问题**，必须分开处理，
否则方案会做偏。下面用 P1 / P2 区分。

### P1：岗位体系本身缺失/不清（"该设什么岗位、要什么人"）

- **本质：** JD / 岗位结构本身缺失、过时或边界模糊。
- **可能症状：**
  - 不知道招什么岗位名；
  - 同一职责跨部门重叠（如电池研发 vs 装备研发的边界）；
  - 同一岗位在不同部门叫法不一；
  - JD 与实际业务脱节（业务已经演进，JD 没更新）。
- **谁的问题：** 岗位体系 / JD 体系的建设问题（组织设计、HR 层面）。
- **解法方向：** 把现有 JD 全量梳理 → 找出缺口 / 重叠 / 过时 → 重建或补全岗位体系。

### P2：领导不会用现有 JD 做用人判断（"JD 怎么用"）

- **本质：** JD 存在，但部门领导**不会把业务需求翻译成岗位要求**，招来的人不对。
- **可能症状：**
  - 有 JD 但看不懂 / 不会用；
  - 业务需求一来，不知道该匹配哪个岗位；
  - 招来的人实际能力与岗位预期不符。
- **谁的问题：** 部门领导的"用人判断力"问题（能力 / 工具 / 流程层面）。
- **解法方向：** 给领导一个工具/流程/skill，帮他把业务需求映射到合适的岗位。

## 三、判断：P1 与 P2 的关系（已用数据确认，但用户已调整方向）

> ⚠️ **方向修正（2026-06-23）**：下面 v1 的判断被用户否决。
> 用户原话：公司是刚突破百人的初创公司，**职位混乱是正常的**，不要去治理。
> 真正要做的能力是：**给定业务场景 + 已有 JD 资料，拆解出"该招什么岗、什么级别的人"**。
>
> 即：不做 P1（治理岗位体系），直接做 P2（拆解招聘需求）。
> 但与 v1 不同的是——P2 不能依赖"干净的岗位地图"，必须**在混乱的真实 JD 之上工作**：
> 把多份模糊 JD 当作知识源，理解它们大致代表的能力画像，再结合业务场景反推用人。

## 六、v2 问题定义（当前生效）

**我们要解决的问题（一句话）：**

部门领导在招聘时，**不会把"我的业务需求/场景"拆解成"我该招什么岗位、什么级别、什么能力的人"**。

**典型场景（用户原话，重要锚点）：**

> "我要招一个采购，但有淘宝采购、京东采购、定制件采购、标准件采购，
>  我到底要哪种采购？我的采购人员需要具备哪种技能、哪些经验？我不清楚。"

这个例子说明，agent 要解决的不是"给一个岗位名"，而是 **「岗位内部维度的细分拆解」**：

- 一个**岗位大类**（如"采购"）在真实业务里会**细分**成多个方向
  （标准件采购 / 定制件采购 / 电商采购 / 技术采购…）。
- 每个细分方向需要的**技能、经验、归属中心、级别**都不同。
- 部门领导恰恰卡在"我知道要招采购，但不知道是哪一种、要什么能力"。

**所以 agent 的核心能力是两层拆解：**

| 拆解层 | 说明 | 输入→输出举例 |
|---|---|---|
| **L1 场景→岗位大类** | 业务场景属于哪条价值链、哪个环节 → 该招什么岗位大类 | "要上第一条产线" → 产线策划 / 装备研发 |
| **L2 大类→细分+画像** | 这个岗位大类在公司实际分哪些细分方向，各自要什么技能/经验/级别 | "采购" → 标准件(供应链知识) / 定制件(懂机加工、能看图) / 技术采购 / 电商采购… |

**skill 要做的核心能力：**

输入：一个业务场景描述（自然语言，例如"我要给客户上第一条产线""我们要把电池能量密度提上去""产线装配总是出问题"）。

处理：
1. 读懂这个业务场景属于公司哪条价值链、哪个环节（见 `business-context.md`）。
2. 在现有 75 份 JD（作为"能力画像知识库"）中检索出相关岗位。
3. 结合业务场景反推：这个场景缺哪些能力？需要什么级别（初级/工程师/高级/总工/负责人）？
4. 输出：建议招的岗位（可能跨部门）、岗位级别、关键能力要求、为什么。

**关键约束（来自用户）：**
- **不要去治理岗位体系混乱**，那是初创正常态，不在范围内。
- JD 资料作为"知识源"用，不是"标准答案"用——JD 本身是模糊的、演进的。
- 最终目标是 skill，当前在反复测试阶段，先把数据和问题定义吃透。
