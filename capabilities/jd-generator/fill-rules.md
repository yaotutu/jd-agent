# JD 填充规则（jd-generator）

> 输入：reasoning 拆解收口后的「岗位画像」（含岗位名/归属/级别/核心能力/职责/JD现状/待确认项）。
> 输出：用 `template.md` 模板填充后的完整 JD，存到 `output/`。
> 本文定义"画像字段 → 模板字段"的映射与填充策略。

---

## 一、字段分类（核心：哪些 agent 填，哪些不碰）

| 模板字段 | agent 填吗 | 数据来源 / 策略 |
|---|---|---|
| 岗位名称 | ✅ | 画像的"岗位名"（如"定制件采购工程师"） |
| 所属部门 | ✅ | 画像的"归属中心"（**必须用真实 14 中心名**，不用 JD 内部乱写的部门名） |
| 直接上级 | ⚠️ | 画像能定则填（如"供应链管理经理"）；推不出 → `[待确认]` |
| 编制日期 | ✅ | 自动填当天日期（YYYY.MM.DD） |
| 一、岗位概述 | ✅ | 基于业务事实写一段话：这个岗在价值链里干什么、起什么作用 |
| 二、岗位职责 | ✅ | **核心产出**：画像拆出的职责分组，每条尽量挂业务依据（可内嵌） |
| 三、任职资格 | ✅ | 画像的能力清单 → 映射到学历/专业/经验/技能/其他 |
| 四、工作关系 | ⚠️ | 内部能推（向谁汇报、与谁协作）；外部能推则填，否则 `[待确认]` |
| 五、工作条件 | ⚠️ | 大多可基于岗位类型推断（研发偏办公室/现场，销售偏出差）；不确定标 `[待确认]` |
| 六、职业发展 | ⚠️ | 晋升方向按级别约定写（见下"级别→晋升路径"）；培训机会固定 |
| 编制人 | ✅ | 填 `jd-agent`（标注是 agent 生成） |
| 审核人 | ❌ | **不碰**，留 `[填写审核人姓名]`（流程性，交给真实审批） |
| 批准人 | ❌ | **不碰**，留 `[填写批准人姓名]` |
| 生效日期 | ❌ | **不碰**，留 `[填写生效日期]` |

**原则：agent 只填"业务/职责/能力"相关字段；流程性字段（审核/批准/生效）一律留占位，交给真实审批流程。**

## 二、任职资格的映射规则（画像能力 → 五类资格）

画像产出的是**两层能力清单**：【核心能力·必须】（角色职能本质）+ 【加分能力·锦上添花】（业务事实技术域）。
分配到任职资格的五个槽位：

| 槽位 | 怎么填 |
|---|---|
| **学历要求** | 按专业领域惯例 + 参考现有同类 JD：研发岗本科及以上，执行/入门可放宽专科。推不出标 `[待确认]` |
| **专业要求** | 对口业务领域：装备研发→机械/机电；电池研发→材料/电化学；采购→机械/供应链等。参考 `jd-profile-index.md` 同中心岗位 |
| **工作经验** | 按画像级别：入门 0-2年、执行层 2-5年、中阶 5年、高阶 8年+。结合画像的"待确认"项调整 |
| **技能要求** | **画像【核心能力·必须】逐条转成技能项**（这是硬要求，必填）；每条挂依据 |
| **加分项**（建议单列） | **画像【加分能力】落在这里**——明确写"以下为加分项，有则优先，不设硬门槛"。避免把多项技术深度堆成硬要求（铁律三） |
| **其他要求** | 软性素质（沟通/抗压/学习能力）+ 出差/现场要求 |

> ⚠️ **模板提示**：现有 `template.md` 的任职资格没有"加分项"独立槽位。
> 填充时把【加分能力】放在"技能要求"末尾，以"**加分（有则优先）：**"前缀单列，与硬技能分开，不混作硬门槛。

**关键：技能要求每一条，都要能挂依据**（铁律二：核心来自角色职能本质，加分来自业务事实，JD 印证）。
同时遵循铁律三——加分项多项技术深度不得写成硬门槛。

## 三、级别 → 晋升路径对照（填"六、职业发展"用）

| 画像级别 | 晋升方向写法 |
|---|---|
| 入门（初级/助理/培训生） | XX助理 → XX工程师 → 高级XX工程师 |
| 执行层（工程师/专员） | XX工程师 → 高级XX工程师 → 资深/专家 |
| 中阶（经理） | XX经理 → 高级经理 → 总监 |
| 高阶（总工/专家/总监） | 专家 → 首席专家 / 或 转 管理路径（总监→中心负责人） |

---

## 四、待确认项的处理（重要）

reasoning 收口时如果还有"待确认项"（如"偏执行还是偏管理"没定），**生成 JD 时**：

- **能合理默认的**：选一个合理默认值填入，并在字段后加注 `(默认：xxx，可调整)`。
- **不能默认的**：该字段填 `[待确认：xxx]`，并在 JD 末尾加一个"生成备注"区块，列出所有待确认项。

**生成备注区块（加在生效日期之后）：**

```
> 📌 生成备注（jd-agent）
> 本 JD 由 jd-agent 基于 [业务事实 + 参考JD] 生成，非人工撰写。
> 主要参考：{{列出参考的现有 JD 文件}}
> 待确认项：
> - {{待确认1}}
> - {{待确认2}}
> 请人工审阅后，填写审核/批准/生效日期，并复核待确认项。
```

---

## 五、文件命名与存储

- **目录**：`output/`（新建，**唯一允许写 JD 的地方**）
- **命名**：`{{岗位名称}}-JD-{{YYYY-MM-DD}}.md`
  - 例：`定制件采购工程师-JD-2026-06-23.md`
- **禁止**：
  - ❌ **绝不修改 `岗位职责说明书/` 下任何原文件**（只读参考源）
  - ❌ 不覆盖 `output/` 里已存在的同名文件（同名加序号 `-2`、`-3`）

---

## 六、生成流程（agent 执行顺序）

1. 确认 reasoning 已收口（画像完整、待确认项已明确）
2. 读取 `capabilities/jd-generator/template.md`（模板）+ 本规则
3. 按"字段分类表"逐项填充：
   - 业务/能力字段 → 从画像取
   - 流程字段 → 留占位
   - 待确认字段 → 按第四节处理
4. 补"生成备注"区块
5. 写入 `output/{{岗位名称}}-JD-{{YYYY-MM-DD}}.md`
6. 向用户报告：文件路径 + 待确认项清单 + 提醒人工审阅

---

## 七、与主流程的关系

jd-generator 是**独立模块**（"打印机"），被 reasoning（"大脑"）在收口后调用：

```
用户需求 → reasoning 拆解（三条铁律）→ 画像收口（核心/加分分层）→ 【调用 jd-generator】→ 产出 JD 到 output/
```

reasoning 的输出是 jd-generator 的输入。两者解耦：
- 改输出格式 → 只动 `template.md`
- 改填充逻辑 → 只动 `fill-rules.md`
- 改拆解逻辑 → 只动 `reasoning-rules.md`
- 互不影响。
