# 可行性初评方法 — AI 路线 vs 软件路线

> 本文档定义：**怎么评估一个机会的 AI / 软件路线可行性**，作为优先级排序的辅助维度。
>
> ROI 高的机会如果可行性低（技术不成熟），也要慎重。本文档给 agent 一套**轻量可行性评估**方法（不替代 AI 小组 / 软件小组的最终评估）。

---

## 一、可行性评分的三个维度

每个路线的可行性按 1-5 分打分：

| 维度 | 含义 | 1 分 | 3 分 | 5 分 |
|---|---|---|---|---|
| **技术成熟度** | 需要的 AI / 软件能力是否成熟 | 实验阶段 | 有开源项目 / SaaS | 标准化产品即开即用 |
| **数据准备度** | 现有数据是否足够支撑方案 | 完全无数据 | 有部分数据，需补 | 数据齐全、结构化 |
| **集成复杂度** | 需要对接多少现有系统 | 单点工具 | 2-3 个系统对接 | 深度集成核心业务系统 |

**可行性 = 三维度的几何平均**，范围 1-5 分。

---

## 二、AI 路线可行性评估细则

### 技术成熟度（按场景分类）

| 场景 | 典型成熟度 | 说明 |
|---|---|---|
| 文档/报告自动生成 | ⭐⭐⭐⭐⭐ | LLM 已成熟，开源/SaaS 多 |
| SOP/知识库问答（RAG） | ⭐⭐⭐⭐⭐ | 技术栈成熟 |
| 图纸识别/参数提取 | ⭐⭐⭐ | 多模态可用，但准确率依赖场景 |
| 实验数据自动分析 | ⭐⭐⭐⭐ | 数据分析+LLM 解释 |
| 参数推荐（DOE） | ⭐⭐⭐ | 学术成熟，工业落地需要定制 |
| 设计方案辅助生成 | ⭐⭐ | 通用方案可做，机械/电装专业方案仍弱 |
| 多步任务自动化（Agent） | ⭐⭐⭐ | 框架成熟，但稳定性需调优 |
| 装配动作识别（视觉） | ⭐⭐ | 数据需求大，工业落地案例少 |
| 客户需求结构化提取 | ⭐⭐⭐⭐ | LLM 强项，配合 RAG |

### 数据准备度评估（针对 AI 路线）

| 数据类型 | 当前状态（推断）| 准备度 |
|---|---|---|
| 装备图纸 | 散落在工程师电脑 / PDM | ⭐⭐ |
| 电池实验数据 | 散落在不同设备/人 | ⭐⭐ |
| SOP 文档 | 有但散落，结构化差 | ⭐⭐⭐ |
| 装配 SOP 视频 | 无系统化 | ⭐ |
| 客户需求文档 | 销售那边有，但口语化 | ⭐⭐⭐ |
| 报价单 / 项目方案 | 历史有，归档格式不一 | ⭐⭐⭐ |
| 质量检验数据 | 纸面 + 部分电子化 | ⭐⭐ |

### 集成复杂度（针对 AI 路线）

| 集成点 | 复杂度 |
|---|---|
| 接入 LLM API（云端）| ⭐（最简单）|
| 接入企业微信/钉钉机器人 | ⭐⭐ |
| 嵌入到 PLM/PDM  | ⭐⭐⭐ |
| 嵌入到 MES | ⭐⭐⭐⭐ |
| 接入现场摄像头（边缘部署） | ⭐⭐⭐⭐⭐ |

## 三、软件路线可行性评估细则

### 技术成熟度（按场景分类）

| 场景 | 典型成熟度 | 说明 |
|---|---|---|
| 工作流引擎（审批/状态机）| ⭐⭐⭐⭐⭐ | 成熟开源/商业产品 |
| 规则引擎（业务规则配置化）| ⭐⭐⭐⭐⭐ | Drools 等成熟 |
| 数据 ETL / 同步 | ⭐⭐⭐⭐⭐ | 成熟方案 |
| 可视化看板 | ⭐⭐⭐⭐⭐ | Grafana / Metabase 等 |
| MES（制造执行系统）| ⭐⭐⭐ | 行业成熟但需要定制 |
| PLM（产品生命周期）| ⭐⭐⭐ | 成熟但实施周期长 |
| ERP 改造 | ⭐⭐ | 大改慎重 |
| BOM 自动生成 | ⭐⭐⭐ | 需要设计 + 软件协同 |
| 版本管理（图纸）| ⭐⭐⭐⭐ | Git + PLM 模块 |
| 客户需求结构化表单 | ⭐⭐⭐⭐⭐ | 表单引擎即可 |

### 数据准备度评估（针对软件路线）

软件路线通常比 AI 路线数据要求低（结构化数据为主）。

| 现状 | 准备度 |
|---|---|
| 已有结构化数据 | ⭐⭐⭐⭐⭐ |
| 散落但可整理 | ⭐⭐⭐ |
| 需要补录 | ⭐⭐ |
| 需要从零采集 | ⭐ |

### 集成复杂度（针对软件路线）

软件路线通常集成更复杂（要嵌入业务流程）。

| 集成点 | 复杂度 |
|---|---|
| 单点工具（如看板）| ⭐ |
| 工作流嵌入（如审批）| ⭐⭐⭐ |
| 与 PLM/MES 深度集成 | ⭐⭐⭐⭐⭐ |

## 四、特殊约束评估（铁律红线）

以下场景**必须额外评估**，可行性分数再高也要慎重：

| 约束类型 | 触发条件 | 处置 |
|---|---|---|
| **数据隐私** | 涉及员工/客户个人信息 | 必须脱敏 / 私有化部署 |
| **客户机密** | 涉及客户工艺参数 / 项目方案 | 需法务 + 客户协议确认 |
| **工艺机密** | 涉及公司核心电池工艺 | 必须内网部署 + 权限控制 |
| **行业合规** | 涉及 ISO / 行业认证 | 必须有审计追踪 |
| **实时性要求** | 要求 < 100ms 响应 | 需边缘部署，不能用云端 LLM |
| **现场环境** | 工厂车间（粉尘/振动/电磁）| 硬件选型特殊 |

**任何一条触发 → 可行性评分自动 -1 分**，并在机会清单"风险与约束"节明确标注。

## 五、可行性评分的输出格式

每个机会在 `opportunity-template.md` 的"基本信息"表格里输出：

| 字段 | 值 |
|---|---|
| AI 可行性 | {{分数}} / 5 |
| 软件可行性 | {{分数}} / 5 |
| 路线推荐 | AI 路线（≥ 4 分）/ 软件路线（≥ 4 分）/ 双路并行（两条都 ≥ 4 分）/ 待评估（两条都 < 4 分）|

**最终路线推荐规则**：

- 两条路都 ≥ 4 分 → **双路并行**（在机会清单里给两个方案，让承接方竞合）
- 只有 AI ≥ 4 分 → **AI 路线**（推荐 AI 3D 事业中心）
- 只有软件 ≥ 4 分 → **软件路线**（推荐行政运营中心信息化组）
- 两条路都 < 4 分 → **待评估**（进入观察池，技术成熟后重评）

## 六、可行性 vs ROI 的关系

**不要只看 ROI 排序，还要看可行性**。

| ROI | AI 可行性 | 软件可行性 | 处置 |
|---|---|---|---|
| ≥ 1.5 | ≥ 4 | ≥ 4 | P0，立即立项（双路并行）|
| ≥ 1.5 | ≥ 4 | < 3 | P0，立即立项（AI 单路）|
| ≥ 1.5 | < 3 | ≥ 4 | P0，立即立项（软件单路）|
| ≥ 1.5 | < 3 | < 3 | **P1**，技术风险高，先做 POC |
| 1.0-1.5 | ≥ 4 | — | P1，季度内立项 |
| < 1.0 | — | — | P2/P3，长期跟踪 |

**核心原则**：可行性 < 3 分的机会即使 ROI 高也要降级（避免做出做不出来的项目）。

## 七、与 AI 小组 / 软件小组的可行性复核

本 agent 给出的可行性评分是**初评**，最终可行性由承接方复核。

**交接时的标注**：

- 机会清单的"交付备注"里标注：本清单的可行性评分为**初评**，最终以承接方（AI 3D 事业中心 / 行政运营中心信息化组）的技术评估为准。
- 如果用户后续拿清单去做立项，需要承接方出**详细的可行性报告**（本 agent 不负责）。
